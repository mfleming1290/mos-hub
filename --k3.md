# MOS / K3s Homelab Reference

This file is the durable reference for agents working with the MOS-managed K3s cluster in this homelab. Prefer this information over generic K3s defaults when they conflict with the actual MOS plugin layout.

## Topology

```text
MOS / control plane
  Hostname: MOS
  SSH: mos.aeyth
  LAN IP: 192.168.50.7
  K3s role: server / control-plane

apps / worker
  Hostname: apps
  SSH: aos.aeyth
  LAN IP: 192.168.50.8
  K3s role: agent / worker
```

The K3s API server is:

```text
https://192.168.50.7:6443
```

Port 6443 must be reachable from worker nodes. Connectivity from `apps` to `MOS` on 6443 was tested successfully.

## Server configuration

On `MOS`:

```text
Directory = /mnt/Apps/system/k3s
Node Mode = Server / Control Plane
Start Arguments = --disable=traefik --disable=servicelb
```

The running process should look like:

```bash
/usr/bin/k3s server
```

The plugin uses a custom K3s data directory, so generic `/var/lib/rancher/k3s/...` paths are usually wrong for this installation.

Important server paths:

```text
Plugin settings:
  /boot/optional/plugins/kubernetes/settings.json

Plugin init script:
  /etc/init.d/k3s

K3s data:
  /mnt/Apps/system/k3s/data

Server token:
  /mnt/Apps/system/k3s/data/server/token

Agent token:
  /mnt/Apps/system/k3s/data/server/agent-token

Node token:
  /mnt/Apps/system/k3s/data/server/node-token

Kubeconfig:
  /mnt/Apps/system/k3s/rancher/k3s/k3s.yaml
```

On the current server, `agent-token` and `node-token` are symlinks to the same underlying `token` file.

To print the worker join token:

```bash
cat /mnt/Apps/system/k3s/data/server/agent-token
```

Use the entire token exactly as printed, including the `::server:` portion.

## Worker configuration

On `apps`:

```text
Directory = /mnt/data/system/k3s
Node Mode = Agent / Worker
```

Join args:

```text
--server https://192.168.50.7:6443 --token <full token>
```

Effective command:

```bash
k3s agent \
  --server https://192.168.50.7:6443 \
  --token '<full token>'
```

Do not trim the token at `::server:`.

## Important: use the MOS plugin, not the generic installer

Do not use the normal K3s installer on MOS:

```bash
curl -sfL https://get.k3s.io | ... sh -
```

MOS does not use systemd or OpenRC in the way the generic K3s installer expects, so the installer reports:

```text
Can not find systemd or openrc to use as a process supervisor for k3s
```

The MOS plugin already installs the K3s binary and provides the SysV init integration needed by MOS.

## Server and agent state separation

Our fork keeps server-mode and agent-mode runtime state separate so changing modes does not overwrite an existing standalone cluster.

Server mode uses:

```text
<Directory>/data
<Directory>/kubelet
<Directory>/rancher
```

Agent mode uses:

```text
<Directory>/agent-data
<Directory>/agent-kubelet
<Directory>/agent-rancher
```

This was specifically added because `apps` previously ran its own standalone K3s server. Its old server state can remain intact while it runs as an agent.

## Service management on MOS

The plugin manages K3s through:

```bash
/etc/init.d/k3s start
/etc/init.d/k3s stop
/etc/init.d/k3s restart
/etc/init.d/k3s status
```

Useful process check:

```bash
ps -ef | grep '[k]3s'
```

Useful API listener check on MOS:

```bash
ss -lntup | grep 6443
```

Expected server listener:

```text
*:6443
```

When `apps` was running a standalone cluster it had its own `10.42.1.0/24` Flannel/CNI state. Agent mode uses separate runtime directories to avoid mixing that old state with the worker configuration.

## Flannel startup behavior

During first bootstrap, K3s may briefly log:

```text
failed to load flannel 'subnet.env' file
/run/flannel/subnet.env: no such file or directory
```

This was transient in our server bootstrap. A few seconds later K3s assigned the PodCIDR, wrote `/run/flannel/subnet.env`, and the core workloads started normally.

Do not treat that early message as a permanent failure unless the node never becomes `Ready` or system pods remain unhealthy.

## Helm integration

MOS also has a Helm plugin. In server mode, when Helm is installed, the Kubernetes plugin exposes:

```text
/root/.kube/config
```

which points to:

```text
/etc/rancher/k3s/k3s.yaml
```

The K3s plugin disables bundled Traefik and ServiceLB by default:

```text
--disable=traefik --disable=servicelb
```

This avoids K3s automatically taking ports 80/443 and conflicting with the MOS WebUI or another ingress setup.

## Common troubleshooting sequence

If a worker does not join:

```text
1. On MOS:
   /etc/init.d/k3s status

2. Confirm API listener:
   ss -lntup | grep 6443

3. Confirm apps can reach:
   192.168.50.7:6443

4. On apps:
   Node Mode = Agent / Worker

5. Start Arguments must contain BOTH:
   --server https://192.168.50.7:6443
   --token <full token>

6. The token must include the complete ::server:... portion.

7. Check the worker plugin Live Log or:
   /var/log/k3s

8. On MOS:
   k3s kubectl get nodes -o wide
   k3s kubectl get pods -A -o wide
```

## Do not assume generic K3s filesystem locations

Generic K3s documentation often references:

```text
/var/lib/rancher/k3s
/etc/rancher/k3s
```

The MOS plugin deliberately redirects most persistent state into its configured Directory. Always inspect the plugin's `settings.json` first and derive paths from that directory.
